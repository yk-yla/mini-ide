# mini-ide 性能专项

本文是性能优化的长期执行基线。后续即使会话上下文被压缩，也必须先读本文，按本文的阶段、约束和验收标准继续，不凭感觉做零散优化。

## 1. 现状与目标

首要问题是搜索交互卡顿：

- 文件名搜索当前快捷键实际为 `Ctrl+Shift+N`，代码中没有 `Ctrl+Shift+M`。本专项不改快捷键，只优化性能。
- 全局内容搜索当前快捷键为 `Ctrl+Shift+F`。文件预览和日志面板内的 `Ctrl+F` 是局部搜索，不属于同一条链路。
- 当前文件索引最多包含 50,000 个文件。基准中，2,928 个真实文件的同步模糊查询耗时约 14-21ms；50,000 个合成文件约 151-343ms，已足以阻塞输入。
- 文件搜索弹窗构造约 36ms。主要瓶颈是主线程中的全量模糊打分和排序，不是弹窗本身。
- 全局内容搜索已在 `QThread` 中读取文件，但首次搜索会重新遍历目录；对话框关闭后缓存丢失。匹配信号到达后，主线程直接逐条创建并更新树节点。
- 运行日志已捕获到与搜索无关的主线程阻塞，例如自动 Git 检查在主线程等待子进程超过 3 秒。这说明需要统一的性能观测和后续全功能巡检。

本专项的用户体验目标：

- 快捷键触发后 100ms 内出现可输入的搜索窗口。
- 输入、删除、移动光标期间主线程不执行全量文件查询。
- 新查询能取消或淘汰旧查询，旧结果不能覆盖新结果。
- 全局内容搜索复用项目级文件索引，常规情况下不重复遍历目录。
- 搜索结果分批进入界面，单次界面刷新保持有界。
- 超过 250ms 的 UI 事件循环延迟有可检索日志；超过 3 秒仍保留线程栈快照。

## 2. 不变量

- 不引入新依赖，不依赖系统必须安装 `rg`。
- 磁盘扫描、文件读取、全量模糊匹配不得在 Qt 主线程执行。
- 文件索引仍由一个项目一个 `FileIndexer` 持有；初次后台构建，watchdog 增量维护。
- 搜索结果排序、大小写、整词、正则、扩展名、噪音文件过滤和 1,000 条上限等既有行为保持兼容。
- 工作区排除规则、隐藏目录和生成目录排除规则继续复用现有实现。
- 所有 worker 必须可停止；窗口关闭时不能出现 `QThread destroyed while thread is still running`。
- 日志只记录耗时、数量、查询长度和状态，不记录用户搜索文本或文件内容。
- 性能优化不能把业务项目服务、Git 或工作区操作搬回主线程。

## 3. 第一阶段：搜索和观测

### 3.1 UI 延迟观测

在主事件循环增加 100ms 心跳，计算实际回调间隔。额外延迟达到 250ms 时，写入 `mini-ide.performance` 警告日志，并做短时间限流，避免持续卡顿时刷屏。现有 1 秒心跳和 3 秒线程栈 watchdog 保留。

性能日志统一使用以下字段：

```text
perf op=<操作> duration_ms=<毫秒> files=<数量> matches=<数量> status=<状态>
```

搜索日志不写查询内容，只写 `query_len`。至少覆盖：文件索引完成、文件查询完成、内容搜索首批结果、内容搜索结束/停止、UI 延迟。

### 3.2 文件索引和文件名搜索

`IndexedFile` 在后台建索引时预计算小写路径、无扩展名文件名和驼峰/分隔符首字母，避免每次查询重复计算。

文件查询使用有界 Top-K 选择，只保留需要展示的候选，不再对所有命中项完整排序。同步 `FileIndexer.search()` 保留给测试和轻量调用，但 GUI 不得直接用它处理非空大查询。

新增可中断的文件查询 worker：

- 每个请求带递增 generation。
- 新输入到来时请求中断旧 worker。
- 只有当前 generation 的结果可以进入界面。
- worker 定期检查中断状态并主动让出执行权。
- 对话框关闭时请求中断全部存活 worker，完成后统一释放。

文件搜索弹窗打开时只展示已有索引的前 150 项，不执行非空全量查询。输入经过约 100-120ms 防抖后交给 worker。文件树过滤入口也复用同一异步查询规则。

### 3.3 全局内容搜索

`ProjectTab` 创建内容搜索对话框时传入当前 `FileIndexer`。索引可用时直接传候选文件快照，跳过重复 `os.walk`；索引尚未完成时才使用现有后台遍历作为兼容回退。

只有未被 `MAX_FILES` 上限截断的完整索引可以作为内容搜索候选。索引达到上限时必须回退后台全量遍历，不能为了速度漏搜文件。

候选快照仍在 worker 内执行扩展名、噪音文件、大小和工作区排除检查，不能因为复用索引而扩大搜索范围。

结果信号只负责进入待渲染队列。主线程由短周期 timer 分批消费：

- 每轮最多处理固定数量的匹配。
- 批量期间暂停树控件重绘。
- 同一文件的命中计数每轮只更新一次。
- 搜索完成后必须先排空队列，再显示最终状态。
- 停止或开始新查询时必须丢弃旧队列。

### 3.4 本阶段验收

- 50,000 文件基准下，文件搜索弹窗构造低于 100ms。
- 非空查询由 worker 执行，主线程调度耗时低于 20ms。
- 50,000 文件查询 worker 的本机基准目标低于 200ms；最差不得超过优化前基准。
- 连续输入时只展示最后一次查询结果。
- 内容搜索使用已有索引时不调用目录遍历。
- 1,000 条内容命中可完整展示，停止、重启和关闭均无线程销毁警告。
- 现有冒烟测试全部通过。

## 4. 第二阶段：全功能巡检

第一阶段稳定后，按以下顺序用 `mini-ide.performance` 和 freeze watchdog 的证据逐项处理：

1. 自动 Git 状态、上游检查、远程 fetch 和文件颜色刷新，重点清除主线程子进程等待。
2. 项目识别、会话恢复、聚合目录和工作区快照，检查启动阶段串行扫描。
3. 文件树展开、刷新、复制粘贴和预览，检查大目录与大文件。
4. 日志批量写入、搜索和高亮，检查高吞吐输出。
5. 服务状态轮询、端口和进程扫描，检查重复系统调用。
6. 语法高亮、Git diff 和其他列表/树视图，检查大数据量渲染。

每个功能必须遵循同一流程：先取得日志或可重复基准，再修改；修改后补回归测试和前后数据。没有证据的重构不计入性能专项。

### 4.1 当前证据与任务

第一阶段打包后的真实运行日志显示：

- 会话恢复时 5 个项目同时启动文件索引，索引完成集中在约 1.8-3.1 秒，期间记录到 3.4 秒 `ui-stall`。
- 多个项目的 3 秒状态/Git 定时器启动时间接近，后续出现 0.5-2.5 秒 `ui-stall`，并与多组 `git_colors` 回调集中出现相关。
- 自动远程 fetch 前仍在主线程同步执行 `is_git_repo` 和 `has_upstream`；分支菜单、切换前 dirty 检查和 Git 视图入口也有主线程 Git 子进程。

第二阶段先执行以下有证据的改动：

- [x] 文件索引通过全局调度器限并发，避免多个 Python 扫描线程同时争用 GIL；项目仍各自持有索引和 watchdog。
- [x] 项目状态/Git 轮询错峰，且不可见项目降低刷新频率；用户主动操作仍立即刷新。
- [x] 自动 fetch 的仓库/上游检查并入后台 worker，清除该路径的主线程 Git 子进程。
- [x] 给 Git 状态 worker 和主线程结果渲染增加耗时日志，确认下一轮瓶颈。
- [x] 重新打包后观察真实 `ui-stall`，并按 freeze 栈处理资源守卫启动扫描。

最新打包运行的 freeze 栈进一步定位到启动阶段的固定路径：

```text
ProjectTab._refresh_status_row
  -> _detect_nginx_status
  -> 首次导入 src.core.nginx_detector
  -> PyInstaller archive extract
```

同时，`ProjectTab.showEvent()` 原先无条件用 `QTimer.singleShot(0, ...)` 刷新状态。会话恢复时即使 Tab 随后不可见，回调仍会执行，绕过“仅可见项目轮询”保护，并可能触发 Nginx 模块的首次加载。该路径实测造成约 `3.46s` 的启动卡顿。

本轮决策：

- `showEvent()` 的延迟回调改为 `_poll_status_if_visible`，回调执行前再次检查可见性。
- `detect_nginx` 改为 `project_tab` 模块级导入，把 PyInstaller 首次解包成本移出状态刷新回调，避免把资源加载和状态查询叠加在同一个 UI 事件中。

本轮验收增加：重新打包并启动后观察至少 30 秒日志，启动阶段不得再出现超过 3 秒的 freeze watchdog；空闲轮询不得产生 500ms 以上的 `ui-stall`。

第一次复验结果：Nginx 首次导入调用栈已消失，但仍出现一次约 `3.2s` 的 freeze。新栈中主线程停留在 Qt `app.exec()`，没有同步 Python 业务调用；freeze 结束前紧邻日志为 `Could not create pixmap from x`。代码确认文件树分支 QSS 使用了 `background: url(x)` 来隐藏图标，导致 Qt 在主线程尝试解析不存在的图片资源。同期文件索引和资源守卫虽在后台运行，但当前没有证据表明它们直接阻塞主线程。

第二次启动修正决策：

- 移除文件树 QSS 中无效的 `background: url(x)`，保留已有的分支背景色以及 `image: none`、`border-image: none`。
- 本轮不调整文件扫描或资源守卫；若移除无效资源后仍卡顿，再依据新的 freeze 栈处理，避免把并发后台任务误判为主线程根因。
- 重新执行完整验证、打包和 30 秒日志观察，要求同时没有 pixmap 警告和超过验收阈值的 UI 卡顿。

第二次打包复验结果：`pixmap` 警告已消失，证明无效 QSS 资源路径已移除；但启动仍出现约 `3.1s` freeze。新栈显示资源守卫在 `psutil.process_iter(["pid", "name", "memory_info"])` 读取进程内存信息，主线程仍停在 Qt 事件循环；文件索引 worker 均在调度信号量上等待或扫描。资源守卫在启动后立即执行第一次全量检查，当前没有自己的耗时日志。

第三次修正决策：

- 资源守卫第一次检查延迟到启动窗口稳定后再执行，避免与会话恢复、文件索引冷启动争用。
- 进程枚举第一遍只读取 `pid/name`，只对命中的 `node.exe` 获取 `memory_info`，不再为所有系统进程读取内存数据。
- 资源守卫增加 `perf op=resource-guard` 耗时日志；后续以真实耗时判断是否还需要进一步拆分或降频。
- 本次问题已从 UI 资源加载切换到系统进程扫描，后续不再继续修改文件树 QSS。

第三次打包复验通过：会话恢复 5 个项目后持续观察超过 30 秒，没有 freeze watchdog、500ms 以上 `ui-stall` 或 pixmap 警告。文件索引完成耗时约 `186-318ms`；资源守卫首次检查约 `445ms`，后续约 `75-91ms`；Git 状态 worker 约 `198-272ms`。本轮启动性能问题验收完成，后续继续按第二阶段顺序处理有日志证据的功能。

进入下一轮前的代码审计确认仍有主线程 Git 路径：

- 分支菜单 `aboutToShow` 同步调用 `list_branches`，一次会启动多个 Git 子进程。
- 本地/远程分支切换前同步调用 `is_dirty`；切换完成回调又同步调用 `git_info.get_info`。
- 合并远程分支选择器同步查询远程分支和当前分支。
- Git 改动查看器构造同步解析仓库根目录；改动签名对每个文件执行 `stat()`；关闭时主线程等待 worker 最长 16 秒。

本轮决策：

- 分支列表、脏状态检查和合并候选全部改为 worker，菜单先显示加载状态，结果回来后再填充。
- GitViewer 的仓库根目录解析、改动签名计算移入概览 worker；关闭窗口只停止刷新并让 worker 脱离 Tab，由应用生命周期回收，不在 UI 线程等待。
- 切换完成提示直接使用已知目标分支，状态栏刷新继续由现有 GitStatusWorker 负责，禁止回调里重新同步查询。
- 本轮补充 Git worker、概览 worker 和主线程列表渲染耗时日志，验收关注菜单/查看器打开期间是否出现 `ui-stall`。

Git 异步化版本首次打包启动后出现一次 `942.5ms` 的 `ui-stall`。时间线显示 `_restore_tabs()` 在单个主线程回调内从 `10:28:40.256` 到 `10:28:41.113` 连续恢复 5 个 Tab，并在每次添加/切换时重复保存会话；首个文件索引完成信号在卡顿结束后才进入主线程。因此本次卡顿根因是会话恢复批处理，不是索引 worker。

会话恢复决策：

- 每次事件循环只恢复一个 Tab，项目之间保留短间隔，让 UI 心跳、绘制和 IPC 能及时处理。
- 恢复期间抑制 `currentChanged` 等信号触发的会话落盘，全部恢复并切回目标 Tab 后统一保存一次。
- 命令行初始项目和资源守卫在恢复完成回调后处理，保持原有顺序，不与恢复任务并发争用。
- 增加单项和整体 `session-restore` 耗时日志；验收要求会话恢复期间不再出现 500ms 以上 `ui-stall`。

会话恢复复验通过：5 个 Tab 总恢复约 `1.1s`，单项约 `80-148ms`，恢复期间没有 `ui-stall` 或 freeze。总耗时允许跨多个事件循环累计，验收以单项主线程占用和事件循环延迟为准。

文件树阶段基准：展开一个直属包含 5,000 个文件的目录，现有 `_populate_children()` 在主线程耗时约 `1764ms`。同一目录的微基准中，`os.scandir` 扫描约 `15ms`，一次性 `addChildren` 挂载 5,000 个基础节点约 `26ms`，说明主要损耗来自 `Path.iterdir/is_dir/is_file` 的逐项对象和系统调用，以及逐节点 `addChild` 更新。

文件树决策：

- 直接子项扫描放入可淘汰的目录 worker，使用 `os.scandir` 一次取得名称、路径和类型。
- UI 回调一次构造节点并用 `addChildren` 批量挂载，期间暂停树更新；Git 染色和删除占位语义保持不变。
- 刷新、普通展开和恢复展开状态都复用异步目录加载；旧 generation 结果不得覆盖新刷新。
- “展开全部”和文件跳转必须适配异步加载，不能为保留旧同步流程重新阻塞主线程。
- 增加目录扫描和渲染耗时日志；5,000 项展开的主线程调度及单次渲染目标低于 200ms，且不能产生 500ms 以上 `ui-stall`。

文件树实现结果：

- 直接子项扫描已由 `_DirectoryLoadWorker` 使用 `os.scandir` 在后台完成，刷新通过 generation 淘汰旧结果。
- 主线程一次构造节点并通过 `addChildren` 批量挂载；恢复展开、文件定位和“展开全部”均按目录 worker 回调逐层续跑。
- 项目关闭会请求中断目录 worker，不在主线程等待；旧 worker 的结果不能覆盖新刷新。
- 性能冒烟加入真实 5,000 文件目录扫描和批量渲染，批量渲染阈值为 200ms。

本阶段验收：会话恢复后不出现超过 3 秒的 freeze watchdog；空闲 30 秒内不出现由周期轮询造成的 500ms 以上 `ui-stall`。

最新打包复验（2026-08-11）：

- 新包 IPC、5 个 Tab 会话恢复和服务状态均正常，目录扫描/渲染日志正常。
- 启动仍捕获一次约 `3.3s` freeze；主线程栈位于 `FileIndexer._apply_snapshot -> _start_watchdog`，具体是 PyInstaller archive 首次导入 `watchdog.observers`。
- 该导入与文件索引完成信号在主线程串行执行，属于启动期资源解包阻塞，不是目录扫描 worker 本身。

修正决策：

- 新增可中断的 watchdog 启动 worker，在后台完成 watchdog 模块导入、Handler 创建和 Observer 启动。
- `FileIndexer._apply_snapshot` 只更新索引并调度 worker，不再同步导入；主线程只接收 Observer 句柄。
- 停止索引时同时请求 watchdog worker 中断；若 Observer 已启动则停止并回收。日志增加 watchdog 启动耗时，继续以无 3 秒 freeze 为验收条件。

搜索现场故障（2026-08-11）：

- 用户在 `D:\me\project\qg` 搜索 7 字符普通文本时，首条结果约 `26094ms`，完成约 `26137ms`，扫描 2,911 个文件、命中 1 条；此速度不可接受。
- 同期另一轮文件名搜索后执行 CLI 退出，日志出现 `QThread: Destroyed while thread is still running`，进程随后重启。根因是应用退出时搜索 worker 仍由 `QApplication` 持有，仅请求中断但没有等待线程结束。
- 这两条是独立问题：内容搜索串行读取过慢；应用退出的搜索线程生命周期不完整。必须分别修复和验证。

搜索故障修正与验收：

- 文件名和内容搜索 worker 加入应用级活动集合；应用真正退出前统一请求停止，并在有界时间内等待搜索线程结束。普通关闭窗口仍只隐藏，不触发该流程。
- 内容搜索先对真实项目取得逐文件耗时证据，再选择并发或读取策略；不能只用合成小文件宣称完成。
- 补充“文件名搜索进行中退出”和“内容搜索进行中退出”回归，要求无 `QThread destroyed`。
- 使用同一 `qg` 项目和同类低命中中文查询复验；目标完成时间低于 5 秒，停止响应低于 500ms，搜索期间界面可交互。

第一次搜索修正打包复验：同一项目、同一查询从约 `26.14s` 降到 `1.32s`，但搜索期间仍记录一次 `551ms ui-stall`。8 个读取线程对所有候选文件同时执行 UTF-8 解码和正则预判，造成 GIL 竞争，未满足界面可交互验收。

第二次修正决策：普通文本在语义安全时先做字节预筛，只对可能命中的文件解码和逐行定位；I/O 并发从 8 降到 4。正则和无法安全字节预筛的大小写不敏感文本继续走完整解码路径，保持搜索语义。

最终复验结果：

- 源码环境同一 `qg` 查询完成约 `491ms`，20ms 测试心跳最大间隔约 `22ms`。
- 最终打包版 GUI 同一查询完成约 `560ms`，扫描 2,911 个文件、命中 1 条；搜索期间没有 `ui-stall` 或 freeze，较故障版 `26.14s` 缩短约 98%。
- 正则搜索启动后立即执行 CLI 退出，进程正常结束，无 `QThread destroyed`、异常或自动重启。
- 最终包启动恢复 5 个 Tab 后观察超过 30 秒，无 freeze、`ui-stall` 或 pixmap 警告；会话恢复总耗时约 `534ms`，watchdog 后台首次启动约 `20ms`。

后续空闲巡检在另一次冷启动捕获 `431ms ui-stall`，与资源守卫第一次 `psutil.process_iter` 的 `422ms` 完全重合。本机基准中，全进程 psutil 枚举约 `321ms`；后台 `tasklist /FI "IMAGENAME eq node.exe"` 约 `364ms`，总耗时相近，但等待外部进程时会释放 GIL。

资源守卫修正决策：Windows 只通过隐藏窗口的 `tasklist` 查询 `node.exe`，再为命中的 PID 创建 `psutil.Process`；不再用 Python 遍历所有系统进程。tasklist 失败或非 Windows 环境回退 psutil，并定期主动让出 GIL。验收仍以空闲无 250ms `ui-stall` 为准。

日志面板基准：一次 flush 1,000 行约 `42ms`，10,000 行约 `788ms`。现有 50ms timer 虽然合并了刷新，但会一次吃完整个待处理列表，突发输出仍会形成 UI 长任务。

日志修正决策：待处理队列改为 `deque`，单次最多渲染 500 行，剩余内容由后续 timer 继续排空；吞吐目标保持至少 10,000 行/秒，单批主线程耗时低于 100ms。增加慢批次性能日志和 10,000 行回归。

语法高亮基准：现有 `PygmentsHighlighter.retokenize()` 在 Qt 主线程读取全文、执行 Pygments 分词并调用 `rehighlight()`。约 478KB Java 文本初次高亮和重新分词分别约 `1022ms`、`1032ms`；约 374KB Python 文本分别约 `853ms`、`938ms`。当前 500KB 阈值会让接近上限的常见代码文件稳定形成 0.8-1 秒 UI 长任务，已超过 250ms 卡顿日志阈值。

语法高亮修正决策：

- 先保留 500KB 高亮上限验证后台分词是否足以消除阻塞；只有实测确认 GIL 仍阻塞事件循环时，才按可交互阈值降低上限。
- Pygments 全文分词和 block 索引构建移入可中断的 `QThread`；主线程只取得文档快照、转换有限种 token 格式并应用结果。
- 每次请求带递增 generation。连续编辑先中断正在执行的旧 worker，只保留最新快照等待执行；旧结果不得覆盖新文档，也不得并发堆积多个分词任务。
- 高亮 worker 由应用级生命周期统一持有和回收。关闭文件只淘汰结果；应用退出必须请求中断并等待，不能再次出现 `QThread: Destroyed while thread is still running`。
- 增加 `syntax-tokenize` 和 `syntax-highlight-apply` 性能日志，不记录文件内容。大文件初次打开的主线程调度目标低于 50ms，结果应用低于 200ms，20ms 心跳最大间隔低于 250ms。
- 回归覆盖约 400-500KB Java/Python 初次高亮、连续编辑只应用末次结果、超过 500KB 自动停用高亮、分词期间关闭和应用退出。

第一版异步高亮复验失败：约 440KB Java 分词线程耗时 `579-602ms`，结果应用约 `122-150ms`，20ms UI 心跳最大间隔 `608-630ms`。Pygments 的正则分词虽然位于 `QThread`，但仍长时间持有 Python GIL，不能满足 250ms 可交互标准；仅换线程不能解决大文件卡顿。

阈值补测结果：约 83KB Java 的分词、应用和最大心跳分别约 `107ms`、`37ms`、`114ms`；约 89KB Python 分别约 `155ms`、`33ms`、`162ms`。约 125-134KB 时最大心跳已达到 `167-243ms`，接近阈值且缺少机器负载余量；约 167-179KB 时达到 `227-320ms`。

修正后的决策：

- 异步分词和 generation 淘汰机制保留，用于避免小文件打开和连续编辑直接同步阻塞。
- `MAX_HIGHLIGHT_BYTES` 降为 100,000 字节，给不同语言、机器负载和打包环境留出余量；超过上限的文件保留打开、编辑、保存和搜索能力，只停用语法着色。
- 回归改为约 80-100KB Java/Python 验证心跳低于 250ms，并用约 400-500KB 文件验证不启动高亮 worker；结果应用仍要求低于 200ms。

源码回归结果：约 83KB Java 的调度、分词、应用和最大心跳分别约 `0.8ms`、`129ms`、`20ms`、`113ms`；约 89KB Python 最大心跳约 `176ms`。约 450KB 文本没有创建高亮 worker；连续请求只应用最新 generation，运行中停止和统一退出回收均通过。同期资源守卫心跳最大约 `51ms`，10,000 行日志分帧最大批次约 `23ms`。`_performance_smoke.py`、`_smoke.py`、`compileall` 和 `git diff --check` 全部通过，待最终包复验。

资源守卫打包复验失败（2026-08-11）：源码线程回归中的 `tasklist` 约 `51ms`，但 PyInstaller 新包启动后同一检查从约 `446ms` 逐步升至 `2.2-2.7s`，并且每轮都会启动一个外部 `tasklist.exe`。该路径既可能造成终端窗口闪现，也可能在系统负载高时拖慢资源守卫线程和退出响应；本轮不能交付。

资源守卫第二次修正决策：Windows 不再启动 `tasklist.exe`，改用 `ctypes` 调用 `CreateToolhelp32Snapshot`、`Process32FirstW/Process32NextW` 读取进程名和 PID，再只为命中的 `node.exe` 创建 `psutil.Process`。保留非 Windows 或 API 失败时的 `psutil.process_iter` 回退，并继续记录 `perf op=resource-guard`。验收要求不产生子进程/终端，单次检查低于 250ms，且 30 秒运行期间无 500ms 以上 `ui-stall`。
