# 需求工作区规则

需求工作区属于聚合目录。聚合定义位于 `<aggregate>/.mini-ide/project.json`，至少包含一个直属组件；组件路径和 `workspaceDirectory` 必须位于聚合根目录内。

## 界面

是否直接在源目录开发或创建需求工作区由用户决定。需求工作区页只展示当前聚合目录的工作区，使用纵向卡片；卡片只保留“进入工作区”，也支持双击进入。“退出工作区”返回聚合源目录。同步、合并、删除交给 AI 按用户授权调用 CLI，不再提供卡片按钮；Review 同样只通过 CLI/API 执行。

处于工作区时，顶层 Tab 标题显示为“聚合名 · 工作区名”（例如“paike · 信创改造”），悬停提示显示工作区路径；退出后恢复为聚合名。启动时按上次会话恢复到工作区的，会弹出非模态提示，说明此时启动、编译使用的是工作区代码。

卡片状态直接读取当前 Git 情况：未提交改动数、任务分支远程备份数量和落后基准分支的提交数。旧的“开发中/评审中”元数据不再作为主要展示状态；完整任务分支默认收起，点击数量后查看。

“落后”列只读取本地 ref，显示任务分支合计落后本地基准分支的提交数，不联网。工作区内的共享项目继续使用源目录，非共享项目使用 Worktree。

## 创建

创建工作区只为勾选的非共享 Git 项目创建 Worktree 和任务分支，并立即推送到 origin 设置上游：

- 未勾选项目不复制。
- 共享项目只引用源目录，不创建 Worktree。
- 新工作区 ID 由任务名称生成无声调拼音，例如“直播系统对接”生成 `zhiboxitongduijie`；不再附加时间戳。
- 默认目录为 `workspace/<拼音任务 ID>/`，任务分支为 `feature/<拼音任务 ID>-<项目 ID>`，并写入 `workspace.json`、`AGENTS.md` 和 `context.md`。
- 生成的 `AGENTS.md` 会声明 `mine-dev-flow` 是需求开发的标准流程；进入工作区后，新 AI 会话由 AI 自动主持该流程，用户不需要主动输入 Skill 名称。
- 进入工作区根目录、工作区组件目录或其下级目录时，mini-ide/CLI 会沿路径向上识别所属工作区；这些路径都在同一个聚合 Tab 内打开，不会生成独立的组件 Tab。需要确认归属时使用 `mini-ide-cli.exe --resolve-target <path>`。
- 目录、同远端任务分支或本地任务分支重名时拒绝创建，由用户调整任务名称；已有 `task-<时间戳>` 工作区保持兼容，不自动改名。
- 组件可在聚合配置中通过 `workspaceCopyFiles` 声明需要从源项目复制到 Worktree 的本地文件，例如 `.env`；只接受项目内相对路径和普通文件。
- 创建前检查 Git 仓库、源目录非 detached HEAD、基准分支和提交可读、任务分支及远端同名分支不存在、Worktree 不重复。
- 所选 Git 项目必须配置 origin。实际创建阶段再联网检查远端同名分支，推送只允许创建不存在的任务分支，不覆盖并发创建的分支；全部推送成功才返回创建成功。
- GUI 预检只读本地仓库和远端分支缓存，不联网、不编译；显示当前项目、检查项、进度和已用时间。30 秒仍未完成时停止等待，保留输入并恢复重试；预检期间可取消或关闭，过期结果不再影响新请求。
- 确认计划后才实际创建目录，按项目显示创建、配置复制和信息写入进度。创建失败或 Git 超时后先完成安全回滚，再恢复操作，避免重试与尚未结束的写入并发。
- 白名单文件缺失、越界、是软链接或目标已存在时创建失败，并回滚本次已创建的 Worktree 和本地分支。元数据写入后若推送失败或未确认成功，保留本地工作区及已有远程分支，返回已推送/未确认项目和工作区路径；核对远端后通过提交推送命令继续，不重复创建或自动删除远端分支。

推荐收尾顺序：用户授权后先 `--workspace-sync-push` 合入最新基准分支并备份任务分支，解决冲突并重新验证，再 `--workspace-merge` 合回基准分支并推送；最后退出目标工作区并执行 `--workspace-delete`。基准分支沿用创建时记录的分支，例如 develop，不固定为 main/master。

示例：

```json
{
  "id": "server",
  "path": "server",
  "type": "java",
  "workspaceCopyFiles": [".env"]
}
```

`workspaceCopyFiles` 不支持通配符，也不会自动复制其它未跟踪或被 Git 忽略的文件。

工作区只允许 `created`、`active`、`reviewing`、`merged` 四种状态；当前创建流程通常直接进入 `active`。

## Review

Review 只通过 CLI/API 提供，界面没有 Review 按钮。它读取每个 Worktree 的：

- 改动文件数和 diff stat。
- 任务分支相对基准的提交。
- 任务分支是否已推送到远端。
- 基准分支是否已包含任务分支。

Review 会据此更新工作区状态。CLI 响应保留编译、健康检查、测试结果字段，但当前 Review 不主动执行这些检查，默认值为“未记录”。

## 提交并推送

- CLI/API 保留独立的提交并推送能力，供自动化按需调用。
- 逐个任务 Worktree 校验当前分支，自动暂存并提交全部业务改动；`workspaceCopyFiles` 管理文件仍按现有规则排除。
- 默认提交信息使用需求名称，CLI 可用 `--message` 指定。
- 无新改动但有本地提交时仍会执行 `git push --set-upstream origin <任务分支>`。
- 不强推，不改写历史；某项目失败后停止后续项目，并保留已经成功的提交和推送。

## 合并代码

通过 `--workspace-merge <target>` 在用户授权后执行：快进合并到源目录的基准分支后，立即推送该基准分支的上游远程；不改写历史：

- 先检查源目录和分支条件；源目录不满足条件时不会提交任务分支。
- 任务 Worktree 有未提交或未跟踪改动时，自动执行 `git add --all` 和 `git commit`，提交信息使用需求名称。
- 所有任务 Worktree 提交成功后，重新检查 Worktree 必须干净且停在任务分支。
- 源目录必须干净且停在创建时记录的基准分支。
- 基准分支必须配置上游远程；推送使用该上游，不强制指定或改写远程地址。
- 基准分支必须是任务分支的祖先，或者任务分支已经包含在基准分支中。
- 在源目录执行 `git merge --ff-only <任务分支>`。
- 合并成功后在源目录执行普通 `git push`，基准分支上已有的其它未推送提交也会一并推送；推送失败会保留本地合并结果，不标记工作区为 `merged`，并停止后续项目。
- 多个项目按配置顺序处理；某个项目失败后，后续项目不再执行。

自动提交阶段任一项目失败时，不会开始合并源分支；已经完成的任务分支提交会保留，便于修复后重试。

所有项目合并并推送成功后工作区状态为 `merged`。

## 同步源分支

- CLI/API 保留独立的同步能力，供只需更新任务分支时调用。

同步只改 Worktree，不改源目录工作区：

- 只要求 Worktree 干净且停在任务分支，不要求源目录干净或停在基准分支。
- 默认只使用源仓库本地基准分支 ref。
- `--fetch` 时，对有上游的基准分支执行 `git fetch --prune`。
- 本地基准和上游一方领先时使用较新的一方；两端分叉时拒绝同步。
- 在 Worktree 执行普通 `git merge`，不 rebase、不改写历史。
- 冲突默认执行 `git merge --abort` 回滚；用户明确要求保留冲突时加 `--keep-conflicts`。
- 成功同步或确认已包含基准提交后，更新 `workspace.json` 对应组件的 `baseCommit`。
- 已合并工作区发生同步后，状态退回 `active`。

## 同步并推送

`--workspace-sync-push <target> [--message text] [--keep-conflicts]` 复用统一的同步并推送流程：

- 先自动提交任务 Worktree 的本地业务改动，但暂不推送。
- 固定先拉取基准分支上游更新，再按“同步源分支”的规则把较新的基准分支合并进任务分支。
- 所有项目都同步成功后，才逐个把任务分支推送到 `origin`；不强推。
- 同步发生冲突时默认回滚本次合并并停止全部推送，本地业务提交保留。
- 用户明确选择保留冲突时，工作区停在合并中状态；解决并提交冲突后，再次执行“同步并推送”完成远程备份。
- 推送阶段跨多个仓库无法保证原子性；某项目推送失败后停止后续项目，并明确报告已经推送和未执行的项目。

## 删除

删除先执行预检：

用户明确授权删除后使用 `--workspace-delete <target>`，命令内部重新执行预检。目标工作区激活时先用 `--close-workspace <target>` 明确退出；删除命令不自动停止服务或切换其他环境。返回目录是否删除及残留任务分支，失败不伪报全部完成。

- 对每个非共享项目确认任务分支已经合并进创建时记录的基准分支。
- 刷新基准分支的远程仓库引用，确认本地基准分支没有尚未推送的提交；未配置上游时检查 `origin/<基准分支>`。
- 工作区目录中的未知文件、流程记录、未提交或未跟踪文件不阻止删除；用户确认删除即表示工作区内容可以整体丢弃。
- 预检通过后先将工作区切为分离状态，解除目录与任务分支的占用关系；不修改工作区文件内容。
- Windows 删除前检查根目录及内部文件的删除访问权限，不跟随符号链接或目录联接。已发现占用时保留全部目录内容，分支清理仍独立执行；重试时可通过保留下来的分离 HEAD 确认已合并。检查后新发生的占用仍可能造成删除失败，按残留结果重试。
- 分别尝试清理整个工作区目录、Worktree 记录、本地任务分支，以及 `origin` 和基准分支上游远程中的同名任务分支；目录被占用或某个分支清理失败，不阻止其余清理。
- 部分失败时分别报告目录和分支的清理结果，日志记录工作区完整路径和剩余分支。
- 不删除源目录、基准分支或任何非本工作区创建的分支。目录或分支清理失败时返回具体残留项。

可能耗时的扫描、Git、文件批处理和工作区生命周期操作不得阻塞 Qt 主线程；GUI 使用 `QThread`，CLI 使用独立工作线程。
